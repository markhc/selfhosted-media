# Repository Guidance

## Project intent

- This is a reusable, public infrastructure-as-code project for self-hosted private-media services, primarily using Ansible and Terraform.
- Treat every service (including Tailscale, Plex, Jellyfin, and qBittorrent) as optional. Changes must preserve explicit service selection and must not provision or configure an unselected service.
- Keep user- and environment-specific values in inputs, inventories, or local configuration rather than embedding them in reusable modules, roles, or playbooks.

## Public-repository safety

- Never commit credentials, API/auth keys, private keys, passwords, cookies, real domains, email addresses, usernames, hostnames, public IPs, account/device IDs, or identifying media/library data. Examples must use unmistakably fake placeholders.
- Do not commit Terraform state, saved plans, `.terraform/`, Ansible vault passwords, SSH material, gathered facts, or inventories/variable files containing real infrastructure details. Add generated and local-only artifacts to `.gitignore` when their tooling is introduced.
- Do not put real secrets in example files, defaults, tests, fixtures, command output, comments, or documentation. Reference environment variables or a documented external secret source instead.

## Documentation

- `README.md` is a short index: project summary, quick start, links to the general guides, and the services table. Do not add detailed setup, configuration, or troubleshooting content to it.
- General guidance that applies across services lives in `docs/` (`getting-started.md`, `tailnet.md`, `operations.md`, `validation.md`, `media-stack.md`). Add a new general guide only for topics that span several services.
- Each service has its own guide at `docs/services/<service>.md` (for example `znc.md`, `thelounge.md`, a future `qbittorrent.md`). When adding a service, create its guide and add a row to the README services table in the same change; update the relevant general guides (deployment targets, data paths, validation) too.
- Service guides use these sections where applicable: what the service does, Enable (selection key and required inventory/vault variables), setup steps, Deploy, network exposure, Data (paths, backups, removal behavior), and troubleshooting.
- Document each fact in one place and link to it with relative Markdown links instead of duplicating it; cross-service topics such as the tailnet policy or OAuth credential belong in the general guides. Keep anchors stable or update every link when renaming a heading.
- Update the matching guide whenever a change alters a service's variables, targets, paths, exposure, or behavior.

## Ansible workflow

- Use `make configure` for controller dependencies, local inventory, and encrypted vault setup. Use `make deploy` for the selected stack, `make deploy-<service>` for one service, and the policy targets in the Makefile when needed.
- Validate with `make check`.
- `ansible/inventories/example/` is the public template; operators copy it to the ignored `ansible/inventories/local/`, which is the default inventory in `ansible.cfg`.
- Prefer Docker for all services. Each service is its own role, tagged with its service key and gated by a flat boolean `<service>_enabled` flag (never a nested per-service map: Ansible replaces rather than merges dictionaries across inventory files and the vault's extra vars), with its own Compose project `selfhosted-<service>` in `/opt/selfhosted/<service>`; never group services into a shared role or project. `site.yml` derives `selfhosted_selected` from the flags of the services in `selfhosted_service_names` (add new services there), refuses the former `selfhosted_services` map, and the `always`-tagged `docker_runtime` runs first when a targeted service is selected. Order roles `nas_tailscale`, `caddy`, then services that depend on them. NAS and `irc_bouncers` service selections belong in separate group variables, not shared `all.yml`; group files keep each service's flag and settings together in one commented section.
- Web services listen on loopback only and publish themselves with `include_role: caddy` / `tasks_from: site` (`caddy_site_name`, `caddy_site_hostname`, `caddy_site_upstream` on a `127.0.0.0/8` loopback address), after their container converges. Never hand-write site blocks or `bind` directives: every site must import Caddy's `selfhosted_private` snippet, and adding a service must not require changes to the caddy role.
- Tailscale runs with host networking, kernel TUN, persistent state, and `TS_AUTH_ONCE=true`; never run native `tailscaled` alongside it. For a fresh NAS, the controller uses the vaulted OAuth credential to generate a 10-minute, one-off, non-ephemeral `tag:nas` auth key. Only the generated key reaches the NAS and it is cleared after enrollment; preserve state for keyless restarts and keep Tailscale SSH disabled.
- Caddy also uses host networking: bind HTTPS only to the discovered Tailscale IP and the optional, explicitly configured RFC1918 LAN IPv4 in `caddy_lan_ip`; disable automatic HTTP redirects (otherwise Caddy can open a wildcard port 80 listener). The Lounge must stay on loopback with private mode and `reverseProxy: true`. Audiobookshelf must stay on loopback (`HOST=127.0.0.1`) as the non-root `audiobookshelf_uid`; its media libraries are explicit, pre-existing host directories mounted at `/media/<name>`, read-only by default, never created or re-owned by Ansible, and never containing or inside the `/opt/selfhosted` deployment root.
- Media-stack services (qBittorrent, qui, Prowlarr, Sonarr, and Radarr) run on the NAS with host networking, each service and instance on its own loopback address (in `127.0.0.0/8`, outside `127.0.0.0/16`) and the application's default port, and reach each other by name (`http://sonarr-anime:8989`); never add a shared Docker network or change the host's `/etc/hosts`. The `media_hosts` helper role (not a service, no container) is the single source of default addresses and builds `media_hosts_addresses` for the services selected on the host; every media container except qBittorrent renders it as `extra_hosts`, so adding a service or instance requires `make deploy` to refresh its peers. qBittorrent never connects to its peers and gets no `extra_hosts`, so a changed peer list never recreates it and reloads its torrents. Those handling media files mount the existing `selfhosted_data_path` at the same `selfhosted_data_container_path` (default `/data`, validated outside system directories, `/config`, and `/tmp`) as the shared `selfhosted_data_uid`/`_gid` with `selfhosted_data_umask`; it is never created, re-owned, or inside `/opt/selfhosted`. Migration from an existing stack is a documented manual step; roles never import or overwrite existing service state.
- Sonarr and Radarr must support several instances (for example Sonarr `tv`/`anime`, Radarr `hd`/`uhd`): one role and selection key per app with an `<app>_instances` list, one Compose project `selfhosted-<app>-<instance>` in `/opt/selfhosted/<app>-<instance>` and one Caddy site per instance, a unique address and vaulted API key per instance, and a separate qBittorrent category and `/data` folders per instance. Removing an instance from the list leaves it running, like disabling a service.
- qBittorrent runs as the shared UID with a read-only root filesystem and `stop_grace_period: 30m`. It rewrites its own config, so Ansible seeds `qBittorrent.conf` only when absent and otherwise enforces only the WebUI loopback, authentication, and vaulted credential keys where the pinned release reads them, `[Preferences] WebUI\*` before 5.3 and `[WebUI]` from 5.3 (stopping the container first when they drift, and removing copies from the other location, so the tag must name a 5.0+ release). Only a PBKDF2 hash of the vaulted password reaches the NAS. Its optional `qbittorrent_mounts` follow the same rules as Audiobookshelf libraries (explicit, pre-existing, read-only by default, never created or re-owned, outside `/opt/selfhosted`), with unique container targets that never overlap the data path, `/config`, `/tmp`, or system directories. Its WebUI is always published through Caddy, also as a fallback while qui is selected.
- qui runs as the shared UID with a read-only root filesystem, the shared data path, and the same extra mounts as qBittorrent (`qui_mounts` defaults to `qbittorrent_mounts`, validated with the same rules), so its paths match qBittorrent's. It binds only to its media_hosts address, restricts `QUI__ALLOWED_HOSTS` to its hostname, `qui`, and that address, uses an HTTPS-only session cookie, and disables self-update. Ansible never seeds or manages `config.toml` (its `sessionSecret` encrypts stored credentials), `qui.db`, the login, or qui instances and proxy keys; those are set up in the web UI.
- Sonarr and Radarr use the hotio images, whose init starts as root only to run the app as the shared UID/GID with the shared umask; keep `cap_drop: ALL` with only `CHOWN`, `SETGID`, and `SETUID` added, and `no-new-privileges`. `<APP>__*` environment variables enforce the instance address and port, SSL off, an empty URL base, `ALLOWEDHOSTS` limited to the instance hostname, `<app>-<instance>`, and its address, authentication required for every address (never `DisabledForLocalAddresses`: Caddy connects from loopback), and the log level. The vaulted `<app>_api_keys` entry reaches the NAS only in the instance's root-only `api.env` (written with `no_log` and no diff). Ansible never seeds or manages `config.xml`, the database, the login, root folders, download clients, or indexers.
- Prowlarr is a single instance that follows the same hotio, capability, `PROWLARR__*` environment, and root-only `api.env` rules as Sonarr and Radarr, with `ALLOWEDHOSTS` limited to `prowlarr_hostname`, `prowlarr`, and its media_hosts address, and the vaulted `prowlarr_api_key`. It handles no media files, so it never mounts the shared data path. Ansible never seeds or manages its `config.xml`, database, login, indexers, applications, download clients, or proxies.
- Pi-hole requires Caddy and `caddy_lan_ip`. It answers DNS only on `pihole_dns_address` (default `caddy_lan_ip`) through `listeningMode: NONE` with `listen-address` and `bind-dynamic`, never on Tailscale, Docker, or loopback interfaces; its web interface stays on plain-HTTP loopback behind Caddy, with no HTTPS listener, NTP, or DHCP. Its single `dns.hostRecord` points every hostname found in Caddy's `sites/*.caddy` files, plus its own, to `caddy_lan_ip`, so it runs after every web service in `site.yml`; never set `dns.hosts` or other UI-managed lists. Enforce settings only through `FTLCONF_*` variables, pass the vaulted `pihole_webui_password` as a Compose secret file (never an environment variable), and keep `cap_drop: ALL` with only the capabilities its start script needs (no `no-new-privileges`: FTL gains file capabilities on exec).
- Cloudflare DNS-01 requires the pinned plugin build and the vaulted `caddy_cloudflare_api_token`; keep the token out of templates/build contexts (the build context holds only the Dockerfile) and preserve `caddy.dockerignore`. A custom hostname needs a separate DNS-only A record; Caddy does not create it.
- Optional ZNC hosts use the same containerized enrollment workflow with one-off `tag:irc` keys; the controller OAuth credential needs that tag permission explicitly. The supplied policy permits NAS/admin access only to the bouncer's TCP 6697, not bouncer access back to the NAS.
- Preserve each service tag's self-ownership in `tagOwners`: a shared OAuth client with multiple tags needs explicit ownership to mint an enrollment key carrying a subset of those tags. Do not assign both service tags to each host as a workaround. Enrollment diagnostics may expose numeric HTTP status, never raw API response bodies, tokens, or keys.
- ZNC uses a non-root slim container and a TLS-required, Tailscale-IPv4-only IRC listener, with no web listener or public port publishing. Its self-signed certificate/key are generated or renewed on deployment using the pinned image, persisted under `tls/`, and mounted read-only in the service; never distribute the private key. Clients must explicitly trust the public certificate. Keep users, networks, SASL credentials, and stable savebuff encryption passwords in the host-keyed vaulted `znc_instances` map. Preserve the separate read-only managed config and writable runtime copy: ZNC requires write access for locking and rewrites its config. Secret-bearing tasks must use `no_log` and suppress diffs; preserve bounded buffers and savebuff state on redeploy.
- Pin every image in role defaults as `<role>_image_repository`, a quoted `<role>_image_tag`, and an optional `<role>_image_digest`; role vars combine them with the shared `container_image` filter (`ansible/plugins/filter`), which refuses invalid parts and an unpinned `latest`, and each role evaluates the result during validation. Caddy's local build uses the same parts for its official builder and base images. The example group files show each image's repository and tag in its service section, equal to the role defaults; change both together. `docs/operations.md#container-images` lists the prefixes only.
- Service flags skip management, not uninstall. Disabling a service leaves its container, data, and any Caddy site running; removal is a documented manual step. Caddy refuses to deploy while containers from the former combined `selfhosted-web` project exist.
- `ansible/playbooks/tailnet.yml` is controller-only and separate from `site.yml`: preview by default, write only with `tailnet_policy_apply=true`, and non-default replacement only with `tailnet_policy_replace_existing=true`. Preserve the default-policy/ETag guards, failed-test detection even on HTTP 200, and `no_log` on all policy/API data. The vaulted `tailscale_oauth_client_id`/`tailscale_oauth_client_secret` are shared by policy and enrollment controller tasks but must never be copied to the NAS.
